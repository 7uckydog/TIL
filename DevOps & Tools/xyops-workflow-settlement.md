# xyOps Workflow로 정산 4단계 파이프라인 구성하기

> Spring `@Scheduled`로 돌리던 정산 배치를 xyOps 워크플로우로 옮기면서
> 정리한 개념과 의사결정 기록.

## xyOps가 뭔가

PixlCore의 오픈소스(BSD-3) job scheduler + workflow 엔진 + 서버 모니터링 플랫폼.
cron을 대체하는 스케줄러에, 잡들을 그래프로 엮는 워크플로우, 모니터링/알림/티켓팅이
한 덩어리로 묶여 있다. 잡 실행은 전부 **플러그인**(JSON over STDIO)으로 돌아가고,
빌트인으로 shell / HTTP(urlplug) / docker / test 플러그인을 제공한다.

- 우리 환경: 자체 호스팅(Portainer)
- 옮긴 대상: Spring `@Scheduled` 정산 배치

## 워크플로우는 언제 쓰나

단발 스케줄 잡은 그냥 이벤트 하나에 트리거만 걸면 된다.
**워크플로우는 잡 여러 개를 순서/조건으로 엮어야 할 때** 쓴다.
이번 케이스가 딱 그거였다 — 정산이 4단계 순차 의존이고, 앞 단계가 실패하면
뒤를 멈춰야 했다.

```
[Schedule Trigger] → ① 정산데이터 송신
                   → ② 상대 데이터 수신 + 대사
                   → ③ 대사 기반 송금예약 생성
                   → ④ 송금 실행 + 성공 시 정산
```

## 내가 한 것

### 1. 각 단계를 독립 이벤트로 등록 → 워크플로우로 묶기

4단계를 각각 별도 이벤트로 만들고, 워크플로우에서 노드로 연결만 했다.
워크플로우는 **순서 제어와 실패 차단**만 담당하고, 실제 일은 각 이벤트가 한다.

> 핵심: 이벤트를 워크플로우에 묶어도, 각 이벤트의 설정(User Field 기본값 등)은
> 그대로 상속된다. 워크플로우 레벨에 같은 필드를 다시 만들 필요 없다.

### 2. 노드 직렬 연결

xyOps는 **기본이 병렬**이다. 트리거에서 나간 와이어들은 제약이 없으면 동시에 뜬다.
그래서 트리거에서 4개를 다 빼면 전부 병렬 실행된다.
순차로 가려면 한 줄 체인으로 이어야 한다.

- 트리거 → ① 만 연결
- ① 출력 폴 → ②, ② 출력 폴 → ③ ... 식으로 잡 노드 출력에서 다음 노드로

### 3. 실패 시 차단

Event/Job 노드 출력에서 빠지는 와이어는 **기본 조건이 `success`**(exit 0 / 2xx).
별도 설정 없이도 앞이 실패하면 뒤로 흐름이 안 간다.
조건 라벨(`success`)은 잡 노드 출력 와이어에만 붙는다.
**트리거에서 나가는 와이어엔 조건 자체가 없어서** 라벨 없는 일자 선으로 보인다(정상).

### 4. 날짜 파라미터를 User Field로

모든 스케줄러는 `offsetDays`(INT)를 받는다. 오늘 기준 N일 전.
기본 1 = 어제(정산/대사는 전일자 처리).

원래 HTTP 플러그인 body에 `{ "offsetDays": 1 }`로 하드코딩했는데,
이러면 특정 날짜를 다시 돌릴 때 body를 직접 고쳐야 한다.
→ **이벤트 User Field로 빼고, body에서 매크로로 치환**하는 구조로 변경.

```json
{ "offsetDays": {{params.offsetDays}} }
```

- 자동 실행: User Field 기본값 1 → 항상 어제자, 손 안 댐
- 재실행: Run 시 폼에서 offsetDays만 바꿔서 실행, body는 영구 1 그대로

## 주의했던 것 (= 삽질 포인트)

### 매크로 치환 문법

xyOps 매크로는 JEXL 기반 + **mustache `{{ }}`** 문법이다.
처음에 `[/params/offsetDays]`로 넣었다가 400을 맞았다.

```
JSON parse error: Cannot deserialize value of type 'java.lang.Long' from Array value
```

→ `[...]`가 그대로 전송돼서 서버(Jackson)가 **배열로 파싱**했다. 치환이 안 먹은 것.
올바른 형식은 `{{...}}`. 변수 경로(`params.offsetDays`)도 정확해야 한다.

> 디버깅 팁: body에 `{ "x": "{{params.offsetDays}}" }`처럼 **따옴표로 감싸서** 보내고
> 실제 전송된 body를 로그에서 확인하면, 치환 동작 여부를 격리해서 알 수 있다.
> 매크로가 끝내 안 먹으면 shell 플러그인 + curl로 가면 확실하다
> (User Field가 대문자 환경변수 `$OFFSETDAYS`로 무조건 주입됨).

### success 판정 기준

urlplug의 성공/실패는 **HTTP 상태 코드**(2xx)가 기본이다.
즉 내부에서 예외 던져 5xx 내려주면 자동으로 error 처리되지만,
**200으로 응답하면서 본문에 실패 코드를 담는 경우는 못 잡는다.**

→ `success_match` / `error_match`(정규식)로 본문을 검사해서 갈음 가능.
정산·송금은 "200인데 실제론 실패"를 놓치면 다음 송금까지 흘러가므로,
`success_match`로 정상 코드(`"resultCode":"SUCCESS"` 등)를 강제하는 게 안전하다.

### Run Now와 Wait

Wait 컨트롤러는 **상대 시간(duration)만** 지원한다. "5시 정각까지 대기" 같은
절대 시각은 없다. 정확한 시각이 필요하면 워크플로우가 아니라 독립 스케줄로 가야 한다.
또 Run Now로 수동 실행해도 **Wait는 설정된 시간만큼 그대로 기다린다.**
테스트할 땐 Wait를 잠깐 짧게 줄이거나, 특정 노드만 Test Selection으로 돌리는 게 편하다.

## 고민하고 선택한 것

### 고정 시각 vs 순서만

각 단계가 1시 / 5시 / 6시 / 15시처럼 정해진 시각이 필요한가를 먼저 따졌다.

| | 워크플로우 체인 | 독립 스케줄 |
|---|---|---|
| 실패 시 뒤 차단 | 자동(`success` 와이어) | 직접 가드 필요 |
| 정각 보장 | X (앞 끝난 시점 + Wait) | O |
| 한 단계만 재실행 | 이벤트로 빼면 가능 | 가능 |

→ 시각이 상대 시스템 타이밍 때문에 고정이어야 하면 독립 스케줄,
순서만 맞으면 되면 워크플로우 체인. (※ 우리 선택은 [실제 선택 채워넣기])

### 인라인 Job 노드 vs 독립 이벤트

실패한 단계만 따로 재실행해야 해서 **독립 이벤트**를 선택했다.
이벤트로 빼면 워크플로우 안 거치고 그 단계만 직접 Run할 수 있고,
단계별 로그/액션/파라미터가 독립적으로 관리된다.
인라인 Job 노드는 워크플로우에 묻혀서 그 단계만 돌리기가 번거롭다.

### 재실행 안전성 (데이터 출처)

워크플로우로 ①→② 연결 시 ①의 output이 ②의 `input.data`로 자동 전달되지만,
②만 따로 Run하면 그 input이 없다.
우리 잡은 단계 간 데이터를 input으로 주고받지 않고,
**각 잡이 `offsetDays` 기준으로 DB에서 직접 읽는** 구조라 이 문제가 없다.
→ 워크플로우 와이어 = 순서/차단 제어, 실제 데이터 = 각 잡이 DB 책임.
이게 단계별 재실행이 안전한 이유.
